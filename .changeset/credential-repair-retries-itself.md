User-facing: If the coach stops answering while you delete a key in Settings, Enduragent now reconnects and checks the key by itself instead of sending you to the Setup screen; it asks you to reload only if the coach is back and still won't use the saved key.

A key delete refused with `runtime-state-diverged` now leaves a retrying repair (`{ retrying, failedResends }`) instead of a repair that needs the athlete, for keys the vault can re-send (`DESKTOP_CREDENTIAL_SLOTS`). While it retries, credential changes and Remove all are blocked, Settings says "The credential was not deleted. Reconnecting to the coach…", and no Setup gate or Reload button shows. A background try first asks the coach for its runtime config and goes no further while that fails, so it does not read secure storage during an outage. Once the coach answers, the try re-reads the saved key states and the runtime config. Only when that read succeeds and the key is still `failed` does it ask main to re-send failed stored keys (`retryFailedCredentials`) and read again. Tries run right away, then after 1, 2, 4, 8 and 15 seconds (capped), and at once when the coach connection reopens. Every controller operation schedules the next try when it settles, so a retrying repair always has one pending. The repair clears when the key is no longer `failed`; after two re-sends in a row leave it `failed`, it becomes the existing "needs the athlete" state with the gate and Reload credential status. The retry keeps running after the athlete leaves Settings, a delete that diverges after Settings closed still starts it, and reopening Settings waits for a running delete. A diverged ChatGPT sign-out and storage-uncertain deletes keep today's manual reload. The credential list and reader moved to `settings/credential-entries.ts`, and the retry scheduler lives in `settings/credential-repair.ts`.
